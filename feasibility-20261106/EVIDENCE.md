## A. Parser

- SQL is parsed by ANTLR4, not JavaCC: `engine/src/main/antlr4/com/arcadedb/query/sql/grammar/SQLParser.g4` (1848 lines) and `SQLLexer.g4` (600 lines). `engine/src/main/java/com/arcadedb/query/sql/antlr/SQLAntlrParser.java:43-47` says the JavaCC parser is retired. The Cypher grammar is a separate pair (`engine/src/main/antlr4/com/arcadedb/query/opencypher/grammar/Cypher25Lexer.g4`, `Cypher25Parser.g4`): a SQL grammar change does not touch Cypher.
- Entry points: `parse: statement SEMICOLON? EOF` (`SQLParser.g4:40-42`), `parseScript: (scriptStatement SEMICOLON?)* EOF` (`:48-50`). `parse` requires one `statement`, so an empty text or a comment-only text (comments go to the hidden channel, `SQLLexer.g4:533-538`) is rejected at `EOF`. The script entry accepts zero statements.
- `SQLAntlrParser.parseWithTree` (`SQLAntlrParser.java:93`): lexer, SLL parse with `BailErrorStrategy`, retry with full LL (`:123-131`), then `SQLASTBuilder.visit(parseTree)` builds the AST; `visitParse` at `SQLASTBuilder.java:437`, `visitSelectStatement` at `:476`.
- Line comment token needs a space after the dashes: `LINE_COMMENT: '--' ' ' ~[\r\n]* ...` (`SQLLexer.g4:533-535`). `--ping`, or `--` directly followed by a newline, is lexed as two MINUS tokens, not a comment.
- `CAST`: no token in `SQLLexer.g4` and no rule in `SQLParser.g4` (a case-insensitive grep for `cast` finds nothing in either). `cast(x as integer)` would parse as `functionCall` (`SQLParser.g4:1499`, `identifier LPAREN expression ...`) and fail at `AS`.
- `::`: no token. `COLON` is `SQLLexer.g4:395`; `inputParameter` is `HOOK | COLON (identifier | FROM) | DOLLAR INTEGER_LITERAL` (`SQLParser.g4:1545-1549`). The only `::` in the lexer is `BUCKET_NAMED_PARAM: B U C K E T COLON COLON IDENTIFIER` (`SQLLexer.g4:420`); a new `'::'` token would not beat it (longer match) but must be checked against map and MATCH uses of `:`.
- JOIN: no `JOIN`, `INNER`, `LEFT`, `OUTER`, `CROSS`, `USING` token (grep of `SQLLexer.g4` finds none); `ON` exists (`:189`). So today `FROM Person p JOIN Company c` parses `p` as the alias and then `JOIN` is an `IDENTIFIER` token where the grammar expects the end, which is the "mismatched input 'JOIN'" of our matrix. Because they are not tokens, `join`, `left`, `inner` are legal type, property and alias names today. A hard token would reserve them for every existing user (`identifier` rule, `SQLParser.g4:1675`, lists the keywords allowed as identifiers).
- `FROM` takes one item: `fromClause: fromItem` (`:1239-1241`), `fromItem` alternatives at `:1243-1258`, the last being `identifier (modifier)* (AS? identifier)?  # fromIdentifier` (`:1258`). `FROM a, b` is not grammar either. `fromClause` is shared by SELECT (`:205`), TRAVERSE (`:226`), UPDATE (`:378`) and DELETE (`:421`), so a join clause belongs in `selectStatement` (`:203-218`), not in `fromClause`.
- The target alias is erased at parse time: `SQLASTBuilder.visitFromIdentifier` (`:1970`) stores the alias; `resolveTargetAlias` (`:395`) rewrites every `alias.property` to `property` using a one-alias stack (`targetAliases`, `:334`, push and pop `:348-355`), because the planner matches index conditions syntactically (issue #7153, comment above `:395`). A join needs several aliases in scope and the alias kept.
- Statement text is the cache key: parsed statements are cached by text with literals extracted into generated parameters (`SQLLiteralParameterizer`, `engine/src/main/java/com/arcadedb/query/sql/antlr/SQLLiteralParameterizer.java:40-140`). A new AST node must be classified there (`parseAndClassify`, `classify`), or its literals are mis-extracted.
- Expressions: `mathExpression` (`SQLParser.g4:1431`), `baseExpression` (`:1445`). `LIMIT` and `SKIP` take a general `expression` (`:1370`, `:1377`), so `LIMIT $1::INTEGER` works once `::` is an expression.
- Existing conversion: method `convert(<type>)` (`engine/src/main/java/com/arcadedb/query/sql/method/conversion/SQLMethodConvert.java:39`) calls `Type.convertOrNull` (`:58-81`), lenient by design (issue #8090): a value that cannot convert gives null. A standard CAST must raise, so it needs its own strict path, not a rename of `convert`.
- The internal `Type` enum (`engine/src/main/java/com/arcadedb/schema/Type.java:67-97`) has BOOLEAN, INTEGER, SHORT, LONG, FLOAT, DOUBLE, DATETIME, STRING, DATE, DECIMAL and more; the mapping from SQL type names (`INT`, `BIGINT`, `VARCHAR(n)`, `NUMERIC(p,s)`, `TIMESTAMP`, ...) does not exist yet.

## D. Edge types as tables

- Edge types are queried as any type: `SELECT FROM <EdgeType>`; `@out`, `@in`, `@rid`, `@type` are lexer tokens `OUT_ATTR`, `IN_ATTR`, `RID_ATTR`, `TYPE_ATTR` (`SQLLexer.g4:312-316`). The planner already has a vertex-centric shortcut for `SELECT FROM E WHERE @out = #x:y` and `@in = ...` (`SelectExecutionPlanner.java:2320-2322`, javadoc `:2365-2420`), which is the building block of a join-to-traversal rewrite.
- Lightweight edges have no record and no properties; a scan of the type's buckets misses them, so the planner walks vertices for those (`EdgeType.holdsLightweightEdges`, `engine/src/main/java/com/arcadedb/schema/EdgeType.java:79`; planner `SelectExecutionPlanner.java:2283-2300`). "Edge type as a table" therefore needs the same two paths.
- The schema does NOT record an edge type's endpoint vertex types. `EdgeType` has `isBidirectional` (`EdgeType.java:41`), `isLightweight` (`:55`), `isUnique` (`:65`) and nothing about from or to types; `CREATE EDGE TYPE` (`SQLParser.g4:586-596`) has no `FROM ... TO ...`; schema JSON writes only `bidirectional`, `lightweight`, `unique` for edge types (`engine/src/main/java/com/arcadedb/schema/LocalDocumentType.java:3004-3021`). The Cypher optimizer estimates degrees from counts, not from declared endpoints (`StatisticsProvider.getAverageDegree`, `engine/src/main/java/com/arcadedb/query/opencypher/optimizer/statistics/StatisticsProvider.java:296`). A property can carry a LINK target type (`Property.getOfType`, `engine/src/main/java/com/arcadedb/schema/Property.java:124`), which would count as a supporting link.
- `CREATE EDGE TYPE ... CUSTOM k = v` exists (`SQLParser.g4:586-596`) and custom metadata persists, so endpoint declarations could start there without a format change; whether that is the right place is a maintainer decision.
- Consequence: a rewrite that recognises the shape `k.@out = a.@rid AND k.@in = b.@rid` needs no endpoint metadata; the warning "no edge connects A and B" cannot be stated for certain without it.

## E. The warning

- Statement cache: `StatementCache` (`engine/src/main/java/com/arcadedb/query/sql/parser/StatementCache.java:38`, `get` `:57`, `getParameterized` `:71`) over `SQLLiteralParameterizer`/`LiteralParameterizer` using a `SegmentedLRUCache` (import `engine/src/main/java/com/arcadedb/query/literal/LiteralParameterizer.java:22`), sized by `SQL_STATEMENT_CACHE` (`engine/src/main/java/com/arcadedb/GlobalConfiguration.java:795`, default 300, per database). Entries are parsed `Statement` objects, so a flag on the statement is bounded by that LRU and disappears with the entry.
- Plan cache: `ExecutionPlanCache` (`.../parser/ExecutionPlanCache.java:90` get, `:115` put), keyed by `Statement.getOriginalStatement()` (`.../parser/Statement.java:577`). Planning runs once per cache miss; plans that depend on input parameters or cannot be cached are re-planned (`SelectExecutionPlanner.java:341-343`), so planning-time logging alone could repeat. A statement-level flag stops that.
- Detection point: planning (`createExecutionPlan`, `:262`) when a join step is built, where both sources and the ON condition are known, and again in the EXPLAIN path.
- Existing once-only warning idioms: `engine/src/main/java/com/arcadedb/graph/IncomingEdgeLookup.java:111,366` (`AtomicBoolean FALLBACK_WARNED`, WARNING first time, FINE after), `.../graph/StripedEdgeList.java:94,279` (`Set<String>` of warned keys), `.../schema/LocalTimeSeriesType.java:77,534` (`AtomicBoolean` per type). `SelectStatement.copy` (`:252`) builds a new object, so the flag must be shared by reference or kept on the cached original: to verify.
- Settings: enum entries in `GlobalConfiguration` with a key `arcadedb.<camelCase>`, a `SCOPE`, a description, a type and a default, e.g. `SQL_STATEMENT_CACHE("arcadedb.sqlStatementCache", SCOPE.DATABASE, ..., Integer.class, 300)` (`:795`) and `QUERY_LITERAL_PARAMETERIZATION("arcadedb.queryLiteralParameterization", SCOPE.DATABASE, ...)` (`:798`, a Boolean switch). A census test requires a key to spell its constant name (`engine/src/test/java/com/arcadedb/Issue10599ConfigurationKeyNamesTest.java:23-29`). A switch would be `SQL_JOIN_WITHOUT_EDGE_WARNING("arcadedb.sqlJoinWithoutEdgeWarning", SCOPE.DATABASE, ..., Boolean.class, true)`.
