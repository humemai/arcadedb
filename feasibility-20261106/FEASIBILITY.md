# Feasibility: a separate `postgresql` query language for ArcadeDB

Date: 2026-11-06. Read-only study. Nothing was built, run or tested; every behavioural statement is from reading code or web pages.

Upstream SHA studied: `fbef2bb1139f34593abbaba5df63ae3491738352` (ArcadeData/arcadedb `main`, 2026-11-05, "fix(sql): preserve conditions in array concat copies (#11322)"). This is newer than the `42b9b66326` of EVIDENCE.md; all file:line references below are at `fbef2bb113`. Worktree: a detached worktree outside the repository (removed at the end). Discussion 11292 was re-read on 2026-11-06: the upstream maintainer (2026-11-05) said they are "in favor of updating our SQL to be more standard", wants a join planned as a traversal when an edge exists, and asked for a once-only warning. Nobody has discussed a second language.

## Summary

1. Recommendation: **spike first, then decide**. The idea is feasible, and a separate language does remove the three risks that came from changing the existing dialect, but it is not cheaper in total. The decision between "extend `sql`" and "add `postgresql`" hinges on one unknown that a short spike can settle (item 4).
2. Registering a language is small: one `QueryEngine` plus one `QueryEngineFactory`, registered in `QueryEngineManager` (public `register(...)`, `QueryEngineManager.java:131`). `mongo` is the minimum example (151 + 52 lines). HTTP, `Database.query/command`, Studio's language list and the wire all take the language as a string, so nothing else is structural. The native image needs one reflection entry (`reachability-metadata.json:643,655` show the pattern).
3. The expensive part is not the registry, it is the execution layer. `SelectExecutionPlanner` takes a `SelectStatement` AST (`SelectExecutionPlanner.java:154,173`), and every reusable step takes SQL AST nodes (`FilterStep(WhereClause, ...)`, `ProjectionCalculationStep(Projection, ...)`, `OrderByStep(OrderBy, ...)`). Cypher did not reuse them: it has its own AST, planner and 62 step classes, and shares only primitives (`AbstractExecutionStep`, `Result`, `ResultSet`, `CommandContext`, the SQL function factory).
4. Realistic architecture: a hybrid. New grammar and binder, translate to SQL AST nodes, plan each single-table source with the existing planner, put new join steps on top, reuse aggregate, order and limit steps. The decisive unknown: whether SQL AST nodes carry enough PostgreSQL semantics (NULL ordering, integer division, strict casts, comparison rules). If not, the language needs its own expression evaluator and the cost rises from L to XL.
5. There is no join step in the SQL executor today (no `*Join*` class under `query/sql/executor`), so INNER/LEFT JOIN is new work in either design. The separate language only removes the grammar, alias and keyword risks, not the join work.
6. Parser: write our own small ANTLR4 grammar for a PostgreSQL subset (ANTLR 4.13.2 is already the engine's parser tool, `engine/pom.xml:99`; no new dependency, native-image proven). Use the community PostgreSQL grammar (`antlr/grammars-v4`, MIT repo, but the PostgreSQL grammar carries the PostgreSQL License, not on ArcadeDB's allow-list by name) as a reference, not as copied source, unless a maintainer signs off. Calcite (9 MB, about 30 dependencies, Janino code generation) and libpg_query (C, JNI) are poor fits. JSqlParser is licence-compatible but is a syntax-only AST with no PostgreSQL semantics.
7. Wire: the existing `{language}` text prefix already routes a statement to any engine (`PostgresNetworkExecutor.java:5015-5031`, execution at `:884`), so the demo over the wire needs no wire change. Making it the default for a session needs a setting and changes to about 25 hard-coded `"sql"` checks in `postgresw`.
8. Size: v0 (SELECT with joins, group by, information_schema, casts, edge-join rewrite, read-only, experimental flag) is **XL if it needs its own evaluator, L to XL if the SQL AST nodes suffice**. The in-place plan of the design note was S+S+M+L+M.
9. Ship as experimental behind a setting (`arcadedb.postgresqlLanguageEnabled`, default off, resolved lazily the way `POLYGLOT_ENGINE_ENABLED` is, `GlobalConfiguration.java:978`), read-only in v0 so `analyze()` is trivial and the security surface is small.
10. Three biggest risks: (1) semantic fidelity, because reusing SQL AST nodes inherits ArcadeDB semantics under a PostgreSQL name; (2) a second SQL stack to maintain next to a 6,830-line planner that changes weekly, and it cuts against the preference for updating the existing SQL that is stated in discussion 11292; (3) scope creep: wire clients send DML, DDL, transactions and catalog queries, so a read-only language needs a routing story on the wire.
11. pgvector (section 8): the surface maps onto the existing LSM_VECTOR index and `vector.*` functions with small rewrites, but the planner has no `ORDER BY <distance> LIMIT k` to index rule today (needs one), index distances differ in value from pgvector for L2 (squared) and inner product (`-(1+dot)/2`) though ordering agrees, and the old lexer already uses `<=>` as null-safe equality (`SQLLexer.g4:328`), which blocks pgvector's cosine operator in the existing dialect and is free in a separate language.
12. Not determined: whether SQL expression nodes can be built without text round-trip for every shape; Calcite native-image status (no source found); the line count of a usable PostgreSQL subset grammar; Studio's behaviour when a language is registered but absent from its static list.

## 1. Language registry

Evidence (all `fbef2bb113`):

- Registry: `engine/src/main/java/com/arcadedb/query/QueryEngineManager.java:55` (class), JVM-wide singleton (`:56`, `:118`). Built-in registrations in the constructor: Java, `sql`, `sqlscript` (`:99-101`); optional modules by class name, tolerant of absence (`:104-107`: opencypher, mongo, graphql, redis; `:122-129` `register(String)` swallows a failed load at FINE); `cypher` is aliased to opencypher (`:109-112`), Gremlin may override it (`:115`). Public `register(QueryEngineFactory)` at `:131` is copy-on-write and lower-cases the language. Lookup `getEngine(language, database)` at `:137-145` throws `IllegalArgumentException` for an unknown name. `isLanguageRegistered` at `:173` exists to bound metric tags (#7122), so a new name is picked up automatically.
- Interface: `engine/src/main/java/com/arcadedb/query/QueryEngine.java:32`. Factory interface `:65` has two methods (`getLanguage`, `getInstance(DatabaseInternal)`). Abstract methods of the engine: `getLanguage`, `analyze(String)` (`:90`), `query` and `command` each in a `Map` and a varargs form (`:141-161`). Optional hooks with safe defaults: `classifyDDL` (`:114`), `handlesItsOwnFailures` (`:127`), `analysisEvaluatesQuery` (`:137`), `registerFunctions`, `isReusable`, `close`.
- `AnalyzedQuery` (`:33-62`): `isIdempotent`, `isDDL`, optional `getOperationTypes` (READ/CREATE/UPDATE/DELETE/SCHEMA) and an optional `execute` that avoids a second parse. This is the security-relevant part: the HTTP streaming path refuses a statement unless `analyze` proves it read-only (`server/.../AbstractQueryHandler.java:978-997`), and the MCP command tool runs writes through `analyze().execute()` (`SQLQueryEngine.java:106-110` comment).
- Dispatch: `LocalDatabase.getQueryEngine(language)` at `LocalDatabase.java:2836` calls the manager (`:2839`); `command` overloads at `:2910-2980`, `query` at `:3019-3059`. `Database.query(String language, ...)` is documented as taking any registered name (`Database.java:102`). So embedded use needs nothing beyond registration.
- HTTP: routes at `server/.../http/HttpServer.java:356` (`POST /command/{database}`), `:364` (`GET /query/{database}/{language}/{command}`), `:366` (`POST /query/{database}`); the language is a body field (`PostCommandHandler.java:224`, `requireStringField(requestMap, "language")`) or a path/query parameter (`GetQueryHandler.java:72`). No allow-list of languages in these handlers; `PostQueryHandler.java:75-79` forwards the string to `database.query`.
- Studio: a static option list, `studio/src/main/resources/static/query.html:62` (`<option value="opencypher">...`), and a MIME map in `studio/.../js/studio-query.js:245`. A new language is usable from the HTTP API at once but absent from Studio until an `<option>` is added.
- Native image: engine factories are loaded by `Class.forName` (`QueryEngineManager.java:125`), so each needs a reflection entry with a no-arg constructor: `native/.../reachability-metadata.json:604` (graphql), `:613` (gremlin), `:643` (mongo), `:655` (opencypher), `:1555` (redis). There is also a `META-INF/services/com.arcadedb.query.QueryEngine$QueryEngineFactory` file in the engine resources listing only the opencypher factory; registration in practice goes through the manager.
- Minimum example: `mongodbw/.../query/MongoQueryEngine.java` (151 lines) and `MongoQueryEngineFactory.java` (52 lines): a factory, `getLanguage`, an `analyze` that returns an `AnalyzedQuery` with operation types, and `query`/`command` that delegate to a wrapper. Mongo's analyze fails safe (unparseable means "assume all write types", `MongoQueryEngine.java:112-113`). GraphQL (162 lines) is the other small one. The full examples are `SQLQueryEngine` (525 lines) and `OpenCypherQueryEngine` (2,053 lines).

What a new language must implement and register: a `QueryEngine` (analyze, query, command in both parameter forms), a factory with a public no-arg constructor, one line in the manager (or a call to `QueryEngineManager.getInstance().register(factory)` from a plugin or a test), a native-image reflection entry, and for a user-facing release a Studio option, a mime mapping, docs, and OpenAPI text (`CoreApiSpec.java:419` lists languages as an example enum). If the engine caches plans, it must also hook schema-change invalidation (`LocalDatabase.getExecutionPlanCache` at `:3247`, `getStatementCache` at `:3242` are SQL's, keyed on SQL text).

Note for a spike: `register` is public, so a test or a separate module can register a language with **zero engine changes**.

## 2. Reuse of the execution layer

What the planner consumes:

- `SelectExecutionPlanner` (6,830 lines) takes a `SelectStatement` in its constructor (`SelectExecutionPlanner.java:154,173`) and builds a `SelectExecutionPlan` in `createExecutionPlan(CommandContext, boolean)` (`:262`). The method plans from a `QueryPlanningInfo` (`QueryPlanningInfo.java:39`) holding AST parts: `Projection`, `WhereClause`, `GroupBy`, `OrderBy` (`:52-82`). It does index selection, bucket pruning, empty-by-construction folding (`:289-297`, `:357-370`), plan caching keyed on the original statement (`:263-268`, `:394-399`).
- Steps take SQL AST nodes and evaluate them themselves: `FilterStep(WhereClause, CommandContext)`, `ProjectionCalculationStep(Projection, ...)`, `AggregateProjectionCalculationStep(Projection, GroupBy, ...)`, `OrderByStep(OrderBy, ...)`, `LimitExecutionStep(Limit, ...)`, `SkipExecutionStep(Skip, ...)`, `FetchFromTypeExecutionStep(typeName, clusters, ...)`. `BooleanExpression.evaluate(Result, CommandContext)` (`BooleanExpression.java:204`) shows the evaluation lives in the AST (`sql/parser` has 230 files, `sql/executor` 198).
- `ExecutionPlan` (`ExecutionPlan.java:30`) is small: `getSteps`, `prettyPrint`, `toResult`, optional `getLimit`. A step is an `ExecutionStepInternal` with pull-based `syncPull(context, n)` (`ExecutionStepInternal.java:59`). So building steps by hand is possible; the plan interface is not the obstacle.

Options:

| Option | What it means | Realistic? | What breaks or is lost |
| --- | --- | --- | --- |
| (a) translate to existing statement objects | PG AST becomes a `SelectStatement` (or ArcadeDB SQL text), existing planner runs it | Yes for single-table queries; the spike path | Joins do not exist in the planner, so a join needs a new branch in the 6,830-line planner or a wrapper above it; PG semantics are those of the SQL AST nodes; the plan and statement caches are keyed on SQL statements |
| (b) build steps directly | New front end calls step constructors itself | Yes, as the join layer | Loses index selection, bucket pruning, EXPLAIN and caching for anything it plans itself unless it calls the planner per source |
| (c) own planner | Own AST, planner, steps, evaluator | Yes, as Cypher shows, but XL | All of it is new; also shares nothing that the old dialect fixes later |

Realistic: **hybrid of (a) and (b)**. For each FROM item, synthesize a single-table `SelectStatement` (with pushed-down predicates) and plan it with the existing planner; put new `HashJoinStep` and `IndexNestedLoopJoinStep` (`AbstractExecutionStep` subclasses, so EXPLAIN works via `prettyPrint`) above; build the remainder (aggregate, order, limit, projection) from SQL AST nodes. This is the same structure as step 2 of the design note, with a different parser in front.

How Cypher did it (`engine/src/main/java/com/arcadedb/query/opencypher`): own grammar (`Cypher25Lexer.g4` 1,642 lines, `Cypher25Parser.g4` 2,495), own AST (`ast/`), own planner (`planner/CypherExecutionPlanner.java`), 62 own step classes (`executor/steps`), own `ExpressionEvaluator` fed by `CypherFunctionFactory`, which wraps the SQL `DefaultSQLFunctionFactory` (`OpenCypherQueryEngine.java:115-117`). It imports only primitives from the SQL executor: `CommandContext` (46 files), `Result` (45), `ResultSet` (40), `AbstractExecutionStep` (40), `ResultInternal`, `WorkGuard`, `OperationHeapLimit`; plus `SelectExecutionPlanner` in two places for index metadata (`optimizer/statistics/StatisticsProvider.java:29,135`, `optimizer/CypherOptimizer.java:78`). It reuses no SQL step and builds no `SelectStatement`. The package is on the order of 10^5 lines of Java (my count 121,061 from the last `xargs` total, possibly one of several batches). So Cypher is option (c); that is the cost if translation fails.

What the three original risks become in a separate language:

- Aliases erased at parse time: the old dialect rewrites an alias-qualified path to a plain property at parse time (`SQLASTBuilder.java` around `:380-410`, `resolveTargetAlias`, issue #7153). A new front end has its own binder and is free of it; but if it hands SQL AST nodes to reused steps, it must emit paths that resolve against a joined row. The design note's claim "joined rows are one property per alias, as MATCH rows are" is still unverified.
- JOIN, LEFT, INNER as legal names: not an issue in a separate grammar.
- Grammar shared with UPDATE, DELETE, TRAVERSE: untouched. `SQLParser.g4` (1,848 lines) and `SQLLexer.g4` (600) stay as they are, which also removes the textual conflict with open PR #10855.

## 3. Postgres wire

- Language selection today: `PostgresNetworkExecutor.getLanguageAndQuery` (`:5013-5032`) defaults to `"sql"` and honours a `{name}` text prefix (`\{(\w+)\}`) that selects any registered engine. For a non-`sql` language the portal has no parsed statement and goes "straight to its own engine" (`:883-885`, `database.command(portal.language, toEngineText(...), ...)`). Result columns are not described ahead of execution for a non-SQL language (`:817`, `:853-868`, `:2703`), so Describe answers from execution.
- So a demo over the wire needs no code change: send `{postgresql} SELECT ...` through pgjdbc. Risk to test: Describe/NoData behaviour for clients that need column metadata first (ORMs, BI tools).
- Hard-coded `"sql"` checks: 25 occurrences of the literal in `postgresw/src/main` (grep count). The relevant behaviours keyed on `"sql"`: session commands (`:1427`, `:3727`), parsed statement reuse at Parse (`:1460`, `:3752`, switch at `:3778`), COPY (`:1380`, `:3081`), empty-result column probing (`:2703`), double-quote rewriting for ArcadeDB's back-ticks (`:5027`, `PostgresQuotedIdentifierRewriter`), Cypher special case (`:1642`). A real PostgreSQL grammar makes the quote rewriter unnecessary (double quotes are standard identifiers). Making `postgresql` the session default needs a setting (e.g. `SET arcadedb.language`) read by `getLanguageAndQuery`, and a decision per behaviour above.
- Catalog: the catalog is answered in front of the engine by text recognition. `handleCatalogQuery` (`:1679-1730`) asks `PostgresCatalog.mightBeAnswered(query)` (`PostgresCatalog.java:651`) first; matched queries are answered from the schema and never reach any engine. `PostgresCatalog` is 4,192 lines, `PostgresCatalogJoin` (305 lines, a nested-loop join over catalog rows, with outer join and an index lookup on equality), `PostgresCatalogSyntax` (760) and `PostgresCatalogExpression` (2,081) hold a hand-written PostgreSQL tokenizer, expression parser and evaluator, with `::` casts. That code is a precedent (and a seed) for PG semantics, and also a duplicate parser that already exists in the tree.
- What routing to a new language changes: catalog and probe queries stay answered by `postgresw` first (no change); only statements that fall through go to the new engine. An engine-side `information_schema` and the wire's own can disagree (same risk already noted in the design note, point 8 of the risk list). Transaction control, `SET`/`SHOW`, `COPY` and empty statements are handled by the wire for `sql` only and would need either the same gates for `postgresql` or a per-statement fallback to `sql`.

Recommendation and reason: (a1). It adds no dependency, matches the project's existing tool and native-image path, keeps the grammar small enough to own (a subset: SELECT with joins, expressions, casts, `CASE`, `IN`, `BETWEEN`, `LIKE`, `IS [NOT] NULL`, aggregates, window-less), and lets the binder be ours. ## 5. Minimal first version

Scope: read-only `SELECT` with INNER/LEFT JOIN, WHERE, GROUP BY/HAVING, ORDER BY, LIMIT/OFFSET, casts, expressions, `information_schema`, edge-join-to-traversal rewrite.

| Component | Status | Notes |
| --- | --- | --- |
| Language registration, factory, `analyze`, native-image entry | New, small | `mongo` is the template; read-only means every analyzed statement is READ |
| PG lexer and parser (ANTLR4 subset) | New | M |
| Parse-tree to PG AST, binder (aliases, scopes, name resolution, `SELECT *`, duplicate column names) | New | L; this is where the alias model lives |
| Expression translation to SQL AST nodes (`CAST`, `::`, `CASE`, `IN`, `BETWEEN`, `LIKE`, `||`, `IS NULL`, arithmetic, functions) | New, adapted | L; semantics gap (item 7, risk 1); alternative is an own evaluator (XL) |
| Single-table access (index choice, buckets, filters) | Reused | Synthesize a `SelectStatement` per source and call `SelectExecutionPlanner` |
| INNER/LEFT JOIN steps (hash, index nested loop, memory cap via `OperationHeapLimit`) | New | M to L; no join step exists in `sql/executor` |
| Aggregate, GROUP BY, HAVING | Reused, adapted | `AggregateProjectionCalculationStep(Projection, GroupBy, ...)`; HAVING and alias mapping are the work |
| ORDER BY, LIMIT, OFFSET, DISTINCT | Reused | `OrderByStep`, `LimitExecutionStep`, `SkipExecutionStep`, `DistinctExecutionStep`; PG NULL ordering must be checked |
| Casts | New | Strict (raise on bad value); the old `convert()` is lenient; `Type` mapping from SQL type names |
| `information_schema` (`tables`, `columns`, `schemata`) | Adapted | Same data as `PostgresCatalog`; a fetch step beside `FetchFromSchemaTypesStep` (the existing `schema:types` family under `sql/executor`) |
| Edge-join-to-traversal rewrite | Adapted | Recognise `e.@out = a.@rid AND e.@in = b.@rid`; target the existing vertex-centric fetch (`SelectExecutionPlanner.java:2320-2418`, `@out`/`@in` equality); EXPLAIN names it |
| Warning for a join with no supporting edge | New, as designed | Unchanged from the design note |
| Wire routing | Adapted | Prefix works today; session default needs a setting |
| Studio option, docs (other repo), OpenAPI text | New, small | Studio list is static (`query.html:62`) |
| Differential test harness | New | Item 6 |

Honest size: **XL** if the language needs its own expression evaluator, **L to XL** if translated SQL AST nodes carry the semantics, in both cases for an experimental v0 without DML. Reasoning: grammar and binder are a fixed, well-understood L; the join steps and edge rewrite are M each and are needed in the in-place plan too; the translator is the open-ended part; tests, docs and wire are about M. The in-place plan in the design note summed to roughly L (S+S+M+L+M) but with the highest regression risk. A calendar guess (judgment, not measured): 8 to 14 weeks for one engineer to a joined-up v0. Treat as an order of magnitude.

Spike, fewest steps, each with a kill condition. All of it outside the engine tree (a test or separate module, `QueryEngineManager.getInstance().register(...)`):

1. Day 1 to 2, registry and parse: register a `postgresql` engine that parses one query, `SELECT a.name, b.title FROM A a INNER JOIN B b ON a.id = b.aid WHERE a.x > 1 ORDER BY 1 LIMIT 5`, with the ANTLR4 subset, and returns the parse tree in `EXPLAIN`. Kill: registration needs an engine change that is not one line.
2. Day 3 to 5, no-join translation: translate single-table queries (WHERE, GROUP BY, HAVING, ORDER BY, casts, CASE) to SQL AST nodes or, as the cheapest variant, to ArcadeDB SQL text, run on the existing engine, and compare 100 queries with real PostgreSQL on the same data. Kill or fork: if more than about 10 percent differ for reasons of semantics (not syntax), the translator route is dead and the choice is an own evaluator (XL) or the in-place plan.
3. Week 2, join: one `HashJoinStep` over two sub-plans from `SelectExecutionPlanner`, one LEFT JOIN, compared with PostgreSQL. Kill: sub-plans cannot be driven with parameters, or the heap cap cannot be honoured.
4. Week 2, wire: the same joined query through pgjdbc using the `{postgresql}` prefix, and the one-line comparison against PostgreSQL's answer. Kill: pgjdbc or psycopg need column metadata at Describe that a non-`sql` language cannot give.
5. Week 2, edge: one edge type, join through it, same rows as the Cypher `MATCH`, EXPLAIN shows the traversal.

Smallest demo that is already informative: step 1 plus a no-join translation of one query, run from a unit test, plus the same text through the wire with the prefix.

## 6. A/B and release plan

Test style available: JUnit 5, `extends TestHelper`, `database.query(language, ...)`, `assertThat` (`CLAUDE.md`; `ExplainStatementExecutionTest`); wire ITs extend `PostgresWireProtocolTestBase` (pgjdbc, server fixture ports); a conformance-suite precedent exists for Cypher: `engine/src/test/java/com/arcadedb/query/opencypher/tck/OpenCypherTCKSuite.java`, with `expected-failures.txt` and `features/` resources. There is no SQL conformance suite in the tree. `e2e/pom.xml:59-67` already depends on Testcontainers, so a real PostgreSQL container in the e2e lane is possible without a new dependency family.

Differential setup (nothing run now):

- Corpus: one frozen file of queries per feature (casts, joins, aggregates, NULL ordering, string and numeric edge cases), plus the query shapes of the six-client wire matrix. A fixture builds the same data in ArcadeDB (types) and in PostgreSQL (tables) from one schema description.
- Oracle 1, the old dialect: for queries both languages express, run `sql` and `postgresql` in one `TestHelper` test, normalise column names, row order (unless ORDER BY), and numeric types, assert equality. Differences are classified, not hidden.
- Oracle 2, real PostgreSQL: Testcontainers `postgres` in the e2e lane (`@Tag("slow")` or its own lane), same corpus over JDBC to both; compare normalised result sets and error classes.
- Oracle 3, DuckDB (MIT, Maven `duckdb_jdbc`, in-process, no Docker): for analytical shapes only, as a second opinion where PostgreSQL and ArcadeDB disagree; test scope only. Not examined: jar size and licence of the bundled native library.
- Parse-only corpus: the PostgreSQL regression-test SQL that `grammars-v4` ships as examples (`sql/postgresql/examples`, PostgreSQL License); measure the share the subset grammar accepts and keep it as a ratchet.
- Ratchet file in the style of the TCK's `expected-failures.txt`: a test that may only shrink the list, and fails when a listed query starts passing without the list being updated.
- Join-to-traversal: same data, join through an edge type equals Cypher `MATCH`, EXPLAIN contains the traversal note.
- Census tests the project already likes (CLAUDE.md "Census tests", `Issue11170MCPToolAnnotationsTest` pattern): every statement kind the grammar accepts has an operation type; no `"sql"` literal in `postgresw` is left unexamined.

Exit criteria to pre-register (proposal; numbers to be fixed before the first measurement, following our timed-study standard):

1. Zero change to existing-dialect results: the whole existing SQL test tree passes unmodified, on JDK 21 (upstream CI) and 25.
2. Acceptance: at least 95 percent of a frozen corpus of the failing cells of the six-client matrix and ORM/BI query shapes parse and run.
3. Equivalence with PostgreSQL: at least 99 percent of the frozen differential corpus equal after the documented normalisation; every remaining mismatch listed as bug, documented divergence, or unsupported; zero silent wrong answers (a mismatch with no error is a release blocker).
4. Equivalence with the old dialect where both express the query: 100 percent, divergences documented.
5. Performance non-inferiority: for queries both languages express, median latency at most 1.1 times the old dialect on both JDKs with the repetitions the claim size calls for; join queries compared with the equivalent Cypher `MATCH`.
6. Security: read-only classification census passes; parse fuzz finds no uncaught `Throwable`; deep nesting is refused cleanly (precedent `SQLQueryEngine.java:101-104`, #9050).
7. Soak: two upstream releases as experimental with no open silent-wrong-answer issue.

Ship as experimental:

- A `GlobalConfiguration` entry, `arcadedb.postgresqlLanguageEnabled` (name to be agreed), default false. Follow the polyglot precedent: `POLYGLOT_ENGINE_ENABLED` is read at resolution time, not at startup, so enabling later works (`QueryEngineManager.java:186-199`, `GlobalConfiguration.java:978`). Registration should therefore be checked lazily in `getEngine`/`isLanguageRegistered`, not in the singleton constructor.
- Name it plainly (`postgresql`); do not claim compatibility beyond the documented subset; a docs page lists what runs and what does not.
- Read-only in v0; any non-SELECT statement raises a clear "not supported in this language" error. Studio option hidden until the flag is on (needs a way for the static list to learn the flag; not determined how).
- The old dialect stays "supported, not recommended for new code" only at promotion time; no removal before a major version, as agreed.

## 7. Risks and unknowns, ranked

1. **Semantic fidelity.** Reusing the SQL AST nodes means ArcadeDB's comparison, NULL, numeric and string rules run under a PostgreSQL name. Unknown how large the gap is; the spike's step 2 measures it. Mitigation: differential corpus; own evaluator if the gap is wide (cost XL).
2. **Two SQL stacks.** A separate grammar, binder and translator to maintain beside a planner (6,830 lines) and a function library that change weekly. A step or AST node change can break the translator without any test noticing; census tests on the translator's reach are needed. It also sits against the "update our SQL" wording in Discussion 11292.
3. **Join engine is new anyway.** No SQL join step exists; the memory limit (`OperationHeapLimit`), index nested-loop choice and `SELECT *` over joins are all open in both designs.
4. **Scope creep on the wire.** Real clients send transactions, `SET`, DDL, DML, `COPY`, catalog queries. A read-only language needs a per-statement fallback to `sql` or a refusal; either choice changes what users see.
5. **Catalog duplication.** `postgresw` already holds a PostgreSQL tokenizer, expression parser and evaluator (`PostgresCatalogSyntax`, `PostgresCatalogExpression`, about 2,800 lines) and its own join; an engine `information_schema` adds a third copy of the schema-to-rows logic, and these can disagree.
6. **Security surface of a second parser.** `analyze()` is the permission gate (`AbstractQueryHandler.java:978-997`); a wrong classification is a privilege bypass. Functions reachable by name are the same function surface as `sql`; v0 should allow-list. Deep nesting and parser fuzzing need the same guards as SQL (#9050). Read-only v0 keeps this small.
7. **Licensing of a seeded grammar.** Only if (a2) is chosen: the PostgreSQL License needs maintainer sign-off and an ATTRIBUTIONS.md entry.
8. **Studio, docs, native image.** Studio language list is static (`query.html:62`); docs live in `arcadedb-docs`; each new factory needs a reflection entry; plan and statement caches need schema-change invalidation if used.
9. **Unknowns:** whether `a.name` on a joined row resolves in reused steps without changes (design-note claim, not verified); Calcite native-image status; whether pgjdbc and psycopg tolerate non-`sql` Describe behaviour; subset grammar size; Studio handling of an unlisted language; the effect on the Python/JVM wheels (none expected, grammar is engine-internal).

## 8. pgvector compatibility for the PostgreSQL-flavoured side

Added 2026-11-06 at the owner's request. Cypher side: already carries the Neo4j vector surface (not re-studied here; `DbIndexVectorQueryNodes.java` is the `db.index.vector.queryNodes` procedure). pgvector facts below come from its README, https://github.com/pgvector/pgvector (version shown there: 0.8.7; the README page I fetched did not state the licence, only linked a LICENSE file, so the licence is unchecked and matters only if we copied text or tests).

What pgvector's README says (cited, not from memory): `vector(n)` up to 16,000 dimensions, HNSW and IVFFlat indexes up to 2,000; `halfvec`, `bit` and `sparsevec` are separate types; operators `<->` (L2), `<#>` (negative inner product, because Postgres only supports ascending order index scans), `<=>` (cosine distance), `<+>` (L1), plus `<~>` Hamming and `<%>` Jaccard for `bit`; `CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops);` with `vector_l2_ops`, `vector_ip_ops`, `vector_l1_ops`; `WITH (m = 16, ef_construction = 64)` as the defaults shown; `SET hnsw.ef_search = 100;` (default 40); the index is used only for `ORDER BY <distance operator> ... ASC` with a `LIMIT`; with approximate indexes "filtering is applied after the index is scanned", so selective filters can return fewer rows, and `hnsw.iterative_scan = strict_order | relaxed_order` (from 0.8.0, `hnsw.max_scan_tuples` default 20000) mitigates it; "For cosine similarity, use 1 - cosine distance"; for inner product, multiply `<#>` by -1.

### (b) Where each piece goes

- Operator tokens. In the **old** lexer, `<=>` is already a token, `NSEQ` (null-safe equality), `SQLLexer.g4:328`; `<`, `<=`, `<>`, `+`, `-`, `->`, `#` are tokens at `:342-399`. So `<=>` cannot be reused for cosine distance in the existing dialect without breaking `a <=> b` null-safe comparisons, while `<->`, `<#>` and `<+>` lex today as `LT MINUS GT` and so on and could become tokens, with a small risk where someone writes `x<-1` or an RID after `<` (`#12:0`). In a **separate PostgreSQL grammar** none of this applies: the operators are new tokens in a new lexer, and `<=>` can mean cosine distance. This is a concrete advantage of the separate language.
- Types. `vector(n)` is a column type in `CREATE TABLE` and a cast target (`'[1,2,3]'::vector`). `Type` has `ARRAY_OF_FLOATS` (`Type.java:118`); the PG front end maps the name and keeps `n` for validation. The string literal `'[1,2,3]'` must be parsed to `float[]` at bind time; pgvector sends it as text over the wire (not checked in the README).
- Index DDL. In the PG grammar `USING hnsw (col vector_cosine_ops) WITH (m = .., ef_construction = ..)` is a new `CREATE INDEX` form, translated to the existing `CreateIndexStatement` path with `LSM_VECTOR` and a METADATA map built from the options; no change to the existing statement is needed.
- Planner path today. `vector.neighbors('index', key, k, opts)` is a **function call** evaluated per row; the planner only knows about it for bucket pruning (`SelectExecutionPlanner.java:2211, 2966, 3031, 3058` comments), and I found no code that recognises `ORDER BY <distance> LIMIT k` as an index search (grep for vector in the planner finds only those pruning sites and an index-plannability comment at `:179`). So `ORDER BY embedding <=> $1 LIMIT 10` has no index path today in either dialect.
- Recognising ORDER BY distance LIMIT. Feasible as a planner rule: ascending `ORDER BY` on a PG distance operator (or on `vector.*Distance`) whose column has an `LSM_VECTOR` index of a matching similarity, plus a `LIMIT`, becomes a fetch step that calls `LSMVectorIndex.findNeighborsFromVector(query, k, efSearch, allowedRIDs, guard)` (`LSMVectorIndex.java:9326`), then applies the rest. Conditions to get right: index similarity equals the operator (cosine index for `<=>`, and so on; otherwise exact scan, as pgvector does); `OFFSET` widens k; `WHERE` becomes the post-filter or the pre-filter set (`allowedRIDs`, `opts.where` in `SQLFunctionVectorNeighbors.java:110-115`, thresholds `VECTOR_INDEX_PREFILTER_MAX_SELECTIVITY`, `GlobalConfiguration.java:1453`) which is a behavioural difference from pgvector's post-filter (ArcadeDB can be better; document it); additional `ORDER BY` columns or a different sort direction disqualify the rule; the distance column projected in `SELECT` must be recomputed or taken from the index score (see (c)). In the hybrid design of item 2 this is one more access path chosen by the per-source planning, and it is easier in the new front end because the PG binder knows the operator and column directly; in the old dialect it would be a rewrite on a function expression inside `SelectExecutionPlanner.optimizeQuery`.

### (c) Semantic differences that need care

- Distance versus similarity. Index results carry a `distance` (`SQLFunctionVectorNeighbors.java:453` builds rows with the property `"distance"`) sorted ascending (`:380`). The conversion is `scoreToDistance` (`LSMVectorIndex.java:7886-7891`): COSINE `2 * (1 - score)`, EUCLIDEAN `1/score - 1`, DOT_PRODUCT `-score`.
- Cosine: JVector scores cosine as `(1 + cos) / 2` (the file states this for DOT_PRODUCT at `LSMVectorIndex.java:4793`; the Cypher conversion `1 - distance / 2` at `DbIndexVectorQueryNodes.java:293` is consistent), so the index distance is `1 - cos`, equal to pgvector's `<=>`. This is derived by arithmetic, not run; test it.
- Euclidean: score is `1 / (1 + d^2)`, so the index distance is the **squared** L2, which `DbIndexVectorQueryNodes.java:286` says in a comment. pgvector's `<->` is plain L2, and `vector.l2Distance` takes a `sqrt` (`VectorUtils.java:672-673`). Ordering agrees, values do not; a projected `embedding <-> $1 AS dist` must be `sqrt` of the index value or recomputed.
- Inner product: the index distance is `-score` with `score = (1 + dot) / 2` for DOT_PRODUCT, which is `-(1 + dot) / 2`, not pgvector's `-dot`. Ordering agrees, values do not; project by recomputing with `vector.dotProduct`. The index warns once when a DOT_PRODUCT index sees non-unit vectors (`LSMVectorIndex.java:4791-4840`), because JVector documents unit length; pgvector's `vector_ip_ops` has no such restriction. This is a possible recall difference, to measure.
- Zero vectors: ArcadeDB returns cosine 0.0 (distance 1.0) instead of NaN (`VectorUtils.java:599-607`); pgvector's README section on this was not fetched.
- Search width. Default beam when neither query nor index sets `efSearch`: floor 100 (`DEFAULT_SEARCH_BEAM_FLOOR`, `LSMVectorIndex.java:222`), growing as 2k for larger k; it used to be 100 only up to 10,000 vectors and then `max(2k, 20)` (issue #10704, recall@10 0.929 vs 0.998 on SIFT 100k, per the comment at `:217-221`). pgvector's default `hnsw.ef_search` is 40 and its upper bound 1000 (`e2_hybrid.py:79`). So an unconfigured ArcadeDB query is wider (higher recall, slower) than an unconfigured pgvector one; a compatibility test must set both explicitly (the benchmark lane does: `l3d_dense.py:7`, `EF_SEARCH = 100`). Whether that exact change shipped in 26.11.1 is not checked here; the constant is in the studied SHA.
- Result count: pgvector with an approximate index plus a selective filter can return fewer than k rows (README); ArcadeDB's `maxDistance` and grouping options can too (`SQLFunctionVectorNeighbors.java:105-113`). Neither is an error.
- Ties and ordering: ArcadeDB sorts by distance only (`:380`); the tie order is unspecified, as in Postgres. Compare as sets with a rank tolerance.
- `find_nearest`: I searched the studied tree for `find_nearest` and `findNearest` and found no match, so I do not know what the owner means; the closest is `vector.neighbors` and `findNeighborsFromVector`.

### (d) Testing compatibility with real pgvector

Nothing is run now. The benchmark tree already has a pgvector lane (`benchmarks/experiments/e2_hybrid.py`, `l3d_dense.py`, with a "PostgreSQL 17 with pgvector and Apache AGE" arm at `e2_hybrid.py:1049`), which fixes the matched operating point (`EF_CONSTRUCTION = 100`, `EF_SEARCH = 100`, `COMPARATOR_M`).

- Same data, same queries: load identical vectors (a small fixed set for unit-style checks, plus a SIFT-like sample for recall), build `hnsw` in pgvector and `LSM_VECTOR` in ArcadeDB at matched `m`, `ef_construction` and `ef_search`, per metric (L2, cosine, inner product).
- Exact oracle first: compute the true top-k by brute force (pgvector without an index, `SET enable_indexscan = off`; or in numpy), and compare **both** systems to it. That separates "ArcadeDB differs from pgvector" from "both approximate".
- Metrics: recall@k against the exact result for each system, and top-k overlap between ArcadeDB and pgvector for each query; compare the projected distance values for the rows both return, after the conversions in (c) (L2 is sqrt of the index value, inner product is `-dot`).
- Semantics probes (small, deterministic): zero vector, identical vector (distance 0), non-unit vectors on a DOT_PRODUCT index, `k` larger than the table, `OFFSET`, a selective `WHERE` with and without iterative scan, NULL vectors, wrong dimension (pgvector errors; ArcadeDB `validateSameDimension` raises).
- Wire probe: the same SQL text, `SELECT id FROM items ORDER BY embedding <=> '[..]' LIMIT 10`, sent with pgjdbc to PostgreSQL and to the `postgresql` language over the wire; bind-parameter form `$1::vector` as the SQLAlchemy/pgvector-python shape (the design note's 1a test list already has `$1::INTEGER`).
- Pre-register (extending item 6): recall within an agreed margin of pgvector at the matched operating point, with repetitions scaled to the claim size; zero silent wrong answers on the deterministic probes; EXPLAIN shows the index path for `ORDER BY distance LIMIT`.

### (e) What could also be added cheaply to the existing dialect

- Cheap, additive, no conflict: `<->`, `<#>`, `<+>` as infix operators rewritten to the existing functions (new tokens plus one expression node; size S to M, same shape as the `::` cast work in step 1a), and a `vector(n)` alias for `ARRAY_OF_FLOATS` in `CREATE PROPERTY`/type names. The `1 - cosine` and sign conventions stay documented in a table.
- Blocked in the existing dialect: `<=>` for cosine distance, because it is `NSEQ` today (`SQLLexer.g4:328`). Options inside `sql`: keep `<=>` as null-safe equality and offer a different spelling, or change its meaning by type (vector operands mean cosine distance), which is a behaviour change to review. In a separate PG language the conflict does not exist; this is the strongest single argument for the separate language on the vector side.
- Medium: `ORDER BY <distance> LIMIT k` recognition (a planner rule in either dialect), and `CREATE INDEX ... USING hnsw ... WITH (...)` as a second spelling of the `LSM_VECTOR` DDL, which touches the shared `CREATE INDEX` grammar and needs the same soft-keyword care as `JOIN`.
- Session `SET hnsw.ef_search`: needs a session-variable mechanism for the engine; today `SET` is a wire-level command (`PostgresSessionCommand`). A per-query `efSearch` option already exists.
- Order of value (judgment): the planner rule is what makes pgvector queries fast; operators alone only make them parse, and without the rule `ORDER BY a <-> b LIMIT k` is an exact scan over all rows.

## Relational view for PostgreSQL users (2026-11-11, the user)

Direction: a front end, not a redesign. Storage, ArcadeDB SQL and Cypher stay; a PostgreSQL-friendly relational view (the wire protocol exists) sits in front of the same records. Document and vertex types are tables, `id` is the primary key, link properties and the two ends of an edge type are foreign keys declared in `information_schema` and `pg_catalog`, edge tables expose `source_id` and `target_id` (`in` is a reserved SQL word), one hop through an edge type is an ordinary join that the planner can run as an adjacency walk, paths and multi-hop queries stay in Cypher, full PostgreSQL compatibility is not promised. Order: read-only (catalog plus SELECT with joins) checked by the acceptance corpus and a client matrix, then writes, then the join-to-traversal planner, then COPY and pgvector-style vectors. Time for the language work: only from December 2026 (the user, 2026-11-08); the corpus can be extended now. Posted on ArcadeData/arcadedb discussion 11292 on 2026-11-11; the acceptance corpus is tracked by humemai/mmdbbench#18. An optional later shape: an edge type declared one-to-many shows as a plain foreign-key column on the child table, with no link table.
