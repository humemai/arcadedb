# The postgresql language: supported syntax (fork prototype)

Fork only (`humemai/arcadedb`, branch `feat/postgresql-prototype`). One row per construct that agents write. A statement that is
not in the table is refused with SQLSTATE `0A000` (never a wrong answer). The answers are compared with PostgreSQL 18.7 by the
parity corpus (`engine/src/test/resources/postgresql/corpus`).

| Construct | State | Notes |
|---|---|---|
| `INSERT ... ON CONFLICT DO NOTHING`, with or without `(column, ...)` | supported | A row that breaks a unique index is skipped and not counted. With a target only the index on exactly those columns is an arbiter; a break of another index is `23505`. A target that no unique index matches is `42P10`. |
| `INSERT ... ON CONFLICT (column, ...) DO UPDATE SET ... [WHERE ...]` | supported | The row that is there is read by the table name or the alias, the proposed row as `EXCLUDED`; a bare column that both have is `42702`. A row that would change what the same statement wrote is `21000`. `DO UPDATE` without a target is `42601`. |
| `ON CONFLICT ON CONSTRAINT`, an expression or a predicate in the target, `ON CONFLICT` on an edge table | refused, `0A000` | Name the columns of the unique index instead. |
| `function(...) OVER ([PARTITION BY ...] [ORDER BY ...])` for `row_number`, `rank`, `dense_rank`, `lag`, `lead`, `first_value`, `last_value` and `count`, `sum`, `avg`, `min`, `max` | supported | The default frame of PostgreSQL: to the last peer of the row, the whole partition without `ORDER BY`. In the select list and in `ORDER BY` only: in `WHERE` or `GROUP BY` it is `42P20`. A name that is no window function is `42883`. |
| An explicit frame (`ROWS`, `RANGE`, `GROUPS`), a named window, `FILTER`, `DISTINCT`, `ntile`, `percent_rank`, `cume_dist`, `nth_value`, a window function in a query with `GROUP BY`, `HAVING` or an aggregate | refused, `0A000` | |
| `a CROSS JOIN b`, chains of them, and mixed with `INNER` and `LEFT` joins | supported | Every pair of rows: a nested loop that holds the right input in memory under the memory cap (`53200` over it), or a hash join when a `WHERE` term over both sides is an equality, as with `FROM a, b`. `CROSS JOIN ... ON` and `... USING` are `42601`. `NATURAL JOIN` stays refused, `0A000`. |
| The memory cap of an operator that keeps rows (hash join build, derived table, `WITH`, set operation, subquery key set) | supported | One operator may keep a sixteenth of the maximum heap of the JVM in estimated row bytes, at least 64 MiB and at most 1 GiB (a JVM with 2 GiB: 128 MiB; with 4 GiB: 256 MiB). Over it the statement stops with `53200` and a hint, never an answer from part of the rows. The JVM property `arcadedb.postgresql.joinMemoryMb` (MiB) sets it. |
| `a RIGHT [OUTER] JOIN b` and `a FULL [OUTER] JOIN b`, with `ON` or `USING` | supported | `RIGHT` keeps the rows of `b` that no row of `a` matches, `FULL` keeps both sides, with `NULL` on the missing side. A `WHERE` term stays above the join, as in PostgreSQL. With `USING` the merged column is `b`'s for `RIGHT` and `coalesce(a, b)` for `FULL`. A hash join (an equality in the condition) or, for `RIGHT` and for `FULL ... ON true`, a nested loop, each holding one input in memory under the memory cap (`53200` over it); never an index lookup or a walk. A `FULL JOIN` whose condition has no equality is `0A000`, as in PostgreSQL, and so is `FULL JOIN ... USING` on columns whose types cannot be hashed. `NATURAL` joins stay refused, `0A000`. |
