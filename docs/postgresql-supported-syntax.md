# The postgresql language: supported syntax (fork prototype)

Fork only (`humemai/arcadedb`, branch `feat/postgresql-prototype`). The table lists constructs added on top of the core of the language, so
a construct with no row here may still run. An unsupported construct is meant to be refused with an error (SQLSTATE `0A000` where the
language recognizes it), not answered differently. Known differences from PostgreSQL are named in the row notes and in the parity corpus
cases marked pending (such as `is-columns-public-rows`: `information_schema.columns` reports a record id column as an identity column).
The answers are compared with PostgreSQL 18.7 by the parity corpus (`engine/src/test/resources/postgresql/corpus`).

Where the language behaves differently from PostgreSQL, and why, is on the [differences page](postgresql-differences.md).
What PostgreSQL's own regression files give, statement by statement, is on the [regression page](postgresql-regression.md).

| Construct | State | Notes |
|---|---|---|
| `CREATE [UNIQUE] INDEX [[IF NOT EXISTS] name] ON t [USING btree] (column [, ...])` | supported | The tree index of the engine. On `source_id`, `target_id`, or a record id only the name is recorded. The referring columns of a foreign key that no key covers have an index that is not unique, so a unique index over them is `0A000`: declare `UNIQUE` in `CREATE TABLE`. The limits are on the [differences page](postgresql-differences.md#create-index). Fork issue #125. |
| `CREATE INDEX ON t USING hnsw (embedding vector_l2_ops \| vector_cosine_ops \| vector_ip_ops) [WITH (m = .., ef_construction = ..)]` | supported | An `LSM_VECTOR` index over a column declared `vector(n)`; the nearest-neighbour queries use it as they use one made with `sql`. |
| `DROP INDEX`, other methods and operator classes, expression and partial indexes, `INCLUDE`, `DESC`, `NULLS`, `CONCURRENTLY` | refused, `0A000` | |
| `CREATE EXTENSION IF NOT EXISTS vector` or `pgcrypto`, `[WITH] [SCHEMA public]` | supported | Runs and changes nothing, in a transaction block too: what the two bring is built in. Every other extension and form is `0A000`. Compared with PostgreSQL 18 (`PostgreSQLCreateExtensionTest`). Fork issue [#231](https://github.com/humemai/arcadedb/issues/231). |
| `CREATE TABLE [IF NOT EXISTS] t (column type [NULL \| NOT NULL] [DEFAULT value] [UNIQUE] [PRIMARY KEY] [REFERENCES ...], ..., [CONSTRAINT name] UNIQUE (...) \| PRIMARY KEY (...) \| FOREIGN KEY (...) REFERENCES ...)` | supported | Makes a vertex type, or an edge type for a link table (below); a unique index for each key. A `DEFAULT` is a constant or a clock function (below); on a `jsonb` column a constant JSON object, and on an array column `'{}'`, `ARRAY[]::type[]`, or a constant array (`PostgreSQLColumnDefaultTest`). `SELECT *`, an `INSERT` without a column list, and the columns and keys in `information_schema` are those of PostgreSQL 18 (`PostgreSQLCreateTableTest`). The types and the limits are on the [differences page](postgresql-differences.md#create-table). Fork issue #118. |
| `source_id text NOT NULL REFERENCES t (rid) ON DELETE CASCADE` and the same for `target_id` | supported | The table is a link table: an edge type between the rows of the referenced tables; deleting a row deletes its edges. `t` is a table of a vertex type, however it was made, that declares no column `rid` of its own (fork issue #240). A table with `REFERENCES` on both `source_id` and `target_id` is a link table: each end takes this form or the form of the next row, and any other form of an end is refused, `0A000`. |
| `source_id bigint NOT NULL REFERENCES t [(column)] [ON DELETE CASCADE \| RESTRICT \| NO ACTION] [ON UPDATE CASCADE \| NO ACTION]` and the same for `target_id`, each end on its own | supported | The column is alone the primary key or a unique key of `t`, and the end has its type. `SELECT`, joins on the key, `INSERT`, `DELETE`, `RETURNING`, and `information_schema` answer as PostgreSQL 18; a key that links point at cannot change unless `ON UPDATE CASCADE`; the rules are held by this language only. See the [differences page](postgresql-differences.md#ends-that-refer-to-a-key). Compared with PostgreSQL 18 (`PgLinkKeyParityIT`, `PgLinkKeyWriteParityIT`). Fork issue [#213](https://github.com/humemai/arcadedb/issues/213). |
| Foreign keys between ordinary tables: `column type REFERENCES t [(column)]` and `[CONSTRAINT name] FOREIGN KEY (column, ...) REFERENCES t [(column, ...)]`, with `ON DELETE` and `ON UPDATE` `NO ACTION`, `RESTRICT`, `CASCADE`, or `SET NULL` | supported | Over one or several columns, also to the table itself. The referred columns are a primary key, a unique constraint, or a unique index (`42830`), of the same type as the referring ones, or both of `smallint`, `integer`, and `bigint`, or both of `text` and `varchar`. Checked at the end of each statement (`23503`); a row with `NULL` in a referring column is not checked. The engine holds the same keys for writes of every language, at commit. A delete of a referred row and an insert that refers to it, in two transactions, do not both commit: the second commit fails, normally with `40001`, where PostgreSQL makes the second statement wait. Compared with PostgreSQL 18 (`PostgreSQLForeignKeyTest`); see the [differences page](postgresql-differences.md#foreign-keys). Fork issue [#228](https://github.com/humemai/arcadedb/issues/228). |
| `DEFERRABLE`, `INITIALLY DEFERRED`, `MATCH`, `NOT ENFORCED`, `SET DEFAULT`, a column list after `SET NULL`, a reference to a record id (`rid`) outside a link table, `ALTER TABLE ... ADD CONSTRAINT` | refused, `0A000` | |
| `[CONSTRAINT name] CHECK (expression)` on a column or a table | supported | Checked by the engine on every write of every language, `23514`, with the names, the catalog entries of `table_constraints` and `constraint_column_usage`, and the errors of PostgreSQL 18 (`PostgreSQLCheckConstraintTest`). No clock, random, or session function and no `timestamptz` value but a comparison of two columns; see the [differences page](postgresql-differences.md#check-constraints). Fork issue [#227](https://github.com/humemai/arcadedb/issues/227). |
| `serial`, `bigserial`, `smallserial` (`serial2`, `serial4`, `serial8`), and `smallint`, `integer`, or `bigint GENERATED { ALWAYS \| BY DEFAULT } AS IDENTITY` columns | supported | Numbers from 1, with gaps; inserts of every language are filled. `information_schema.columns` and `pg_attribute` report the columns as PostgreSQL does. Compared with PostgreSQL 18, psycopg, and SQLAlchemy (`PostgreSQLSerialColumnTest`); see the [differences page](postgresql-differences.md#serial-and-identity-columns). Fork issue [#221](https://github.com/humemai/arcadedb/issues/221). |
| `CREATE TABLE` in a transaction block | supported | Runs at once, and other sessions see the table before the commit. A rollback drops it if it is still empty. Compared with PostgreSQL 18, psycopg, and SQLAlchemy `create_all` (`PostgreSQLCreateTableInBlockTest`); see the [differences page](postgresql-differences.md#create-table). Fork issue [#229](https://github.com/humemai/arcadedb/issues/229). |
| `CREATE INDEX` in a transaction block | supported for a table that the same block made | A rollback drops the table with its indexes, under the same rules as the table alone. `create_all` of SQLAlchemy for a model with an index runs on its defaults (`PostgreSQLCreateTableInBlockTest`, compared with PostgreSQL 18). On a table that the block did not make: `0A000`, with a hint to run it in autocommit; see the [differences page](postgresql-differences.md#create-index). Fork issue [#277](https://github.com/humemai/arcadedb/issues/277). |
| `ALTER TABLE [IF EXISTS] t` with `ADD [COLUMN] [IF NOT EXISTS] column type [NULL \| NOT NULL] [DEFAULT value]`, `ALTER [COLUMN] c SET DEFAULT value` or `DROP DEFAULT`, and `ALTER [COLUMN] c SET` or `DROP NOT NULL` | supported | The rows that exist end up as PostgreSQL 18 leaves them, in autocommit, on a table that `CREATE TABLE` made; every other action is `0A000`. See the [differences page](postgresql-differences.md#alter-table). Compared with PostgreSQL 18 (`PostgreSQLAlterTableTest`). Fork issue [#230](https://github.com/humemai/arcadedb/issues/230). |
| `varchar(n)` and `numeric(p[,s])` (`character varying(n)`, `decimal(p,s)`) columns | supported | As PostgreSQL: a number is rounded to the scale (`22003` if it does not fit), a string over the length is `22001` unless the excess is spaces, and `information_schema.columns` and `pg_attribute` report the length, the precision, and the scale. The engine applies them to writes of every language; see the [differences page](postgresql-differences.md#lengths-and-precision). Compared with PostgreSQL 18 (`PostgreSQLTypeModifierTest`). Fork issue [#226](https://github.com/humemai/arcadedb/issues/226). |
| `TEMP`, generated columns, identity options other than the defaults, `INHERITS`, `PARTITION BY`, `LIKE`, `CREATE TABLE ... AS`, `char(n)`, a type modifier on an array, and type modifiers other than `varchar(n)`, `numeric(p,s)`, and `vector(n)` | refused, `0A000` | The position of the refusal is in the error. |
| Values of a `jsonb`, array or `bytea` column: a literal (`'{a,b}'`, `'{"k": 1}'`, `'\x0aff'`), `ARRAY[...]`, a cast (`'{a}'::text[]`, `::jsonb`, `::bytea`), `$n` | supported | PostgreSQL's input rules and SQLSTATEs. A `$n` takes a text, or the Java value (`List` or array, `Map`, `byte[]`). On the wire `ParameterDescription` announces `jsonb`, `bytea`, the array type, and `real[]` for a `vector`, and a text of no declared type is read by the type of the column. The record holds it in the class of its property, so `sql` and openCypher read the same value. A `jsonb` object keeps the order of its keys as written (PostgreSQL sorts them); a decimal in it is stored as a double when a double holds the same number. |
| Values of a `vector` column (an `ARRAY_OF_FLOATS` property): `'[1,0,0]'`, `ARRAY[1,0,0]`, `::vector`, `$n` with a `float[]`, a list or a text | supported | pgvector's rules; wrong dimensions for the `LSM_VECTOR` index of the property are `22000`. The distances and a few written values are compared with a pgvector server (`PgVectorParityIT`); the rest follows pgvector's documented behaviour. |
| The distance operators `<->`, `<=>`, and `<#>`, and `ORDER BY embedding <=> $1 LIMIT k` | supported | With an `LSM_VECTOR` index of the metric of the operator (`EUCLIDEAN`, `COSINE`, `DOT_PRODUCT`), one ascending distance in `ORDER BY`, a `LIMIT`, and no `WHERE`, the index supplies the nearest rows, so the result is approximate; `EXPLAIN` names the search. Every other form is an exact scan. A CI test holds the mean recall at 10 of each operator at 0.90 or more at the default settings, on 10,000 random unit vectors of 64 dimensions (`VectorSearchRecallTest`). `DOT_PRODUCT` is meant for unit vectors. |
| Values of an `EMBEDDED OF T`, `LIST OF T`, or `MAP OF T` column, `T` a document type: an object, an array of objects, an object of objects | supported | Stored as embedded documents of `T`, which `sql` and openCypher read as such, and read back as written, without `@type` and `@cat` (`EmbeddedWriteTest`). An object that the type would change is refused, `0A000`; see the [differences page](postgresql-differences.md#embedded-documents). Fork issue #145. |
| Values of a `date[]` or `timestamp[]` column (`LIST OF DATE`, `LIST OF DATETIME` and its other precisions): `'{2026-01-05,2026-02-01}'`, `ARRAY[...]`, a cast, `$n` | supported | The input rules of `date` and `timestamp`, with their SQLSTATEs; the writes of `values-writes.tsv` are compared with PostgreSQL 18 (`PgParityIT`). The catalog and the wire report `_date` and `_timestamp`. `CREATE TABLE` declares the columns as `date[]` and `timestamp[]`, a `LIST OF DATE` and a `LIST OF DATETIME_MICROS`, compared with PostgreSQL 18 (`PostgreSQLCreateTableTest`). A list of links stays `text[]` and is not written. Fork issues #146 and #155. |
| `timestamptz` (`timestamp with time zone`): columns, keys, indexes, casts, literals, comparisons with `date` and `timestamp`, interval arithmetic, `extract`; `Z`, `UTC`, or an offset (`+02`, `+0200`, `+02:00`) after a time, in a text and in a parameter; a datetime with a zone as a parameter | supported | A `DATETIME_MICROS` property holds the instant as its time in UTC, which is what `sql` and openCypher read. It is shown in the session's time zone, as PostgreSQL shows it (`2026-03-01 19:00:00+09` in `Asia/Seoul`), and a text without a zone is a local time of that zone, with PostgreSQL's rules for the times that a daylight saving change skips or repeats; `extract`, the casts with `date` and `timestamp`, and the months and days of interval arithmetic use the zone too (fork issue [#270](https://github.com/humemai/arcadedb/issues/270), `PostgreSQLTimeZoneTest`). A `timestamp` ignores a zone after its text, as PostgreSQL does. Refused: a zone name or abbreviation in a text, `AT TIME ZONE`, a `timestamptz[]` column, and a time before the year 1 or after 9999 in UTC. An offset of 16 hours or more is `22009`. Compared with PostgreSQL 18, pgjdbc, psycopg, and SQLAlchemy (`PostgreSQLTimestampTzTest`). Fork issue [#223](https://github.com/humemai/arcadedb/issues/223). |
| The clock: `now()`, `CURRENT_TIMESTAMP[(p)]`, `transaction_timestamp()`, `LOCALTIMESTAMP[(p)]`, `CURRENT_DATE`, also after `DEFAULT` (without a precision) on a `date`, `timestamp`, or `timestamptz` column | supported | One value for each transaction, read as it begins, as in PostgreSQL; a statement outside a transaction is its own. For a transaction that a caller of the engine API began, the first statement of the language in it reads the clock. In the schema the default is `sysdate()` of ArcadeDB `sql`, so a record that another language creates takes the time too (in UTC). All of them work in any time zone of the session: `CURRENT_DATE`, `LOCALTIMESTAMP`, and a clock default on a `date` or `timestamp` column read the time in it (fork issue [#237](https://github.com/humemai/arcadedb/issues/237)), and `now()`, `CURRENT_TIMESTAMP`, `transaction_timestamp()`, and a default on a `timestamptz` column are instants that are shown in it (fork issue [#270](https://github.com/humemai/arcadedb/issues/270)). `CURRENT_TIME`, `LOCALTIME`, `statement_timestamp()`, and `clock_timestamp()` are refused, and over the wire so is the spelling `pg_catalog.now()`, which the server reads as a catalog probe: write `now()`. Compared with PostgreSQL 18, pgjdbc, psycopg, and SQLAlchemy (`PostgreSQLCurrentTimeTest`). Fork issues [#222](https://github.com/humemai/arcadedb/issues/222) and [#190](https://github.com/humemai/arcadedb/issues/190). |
| The time zone of a session, over the PostgreSQL protocol: the `TimeZone` startup parameter, `SET TIME ZONE value`, `SHOW TimeZone` | supported | Read as PostgreSQL reads it: a name in any case, a number of hours east of UTC, an interval, or a POSIX offset, which counts west. `22023` for a value that names no zone. pgjdbc sends the zone of its Java process as the startup parameter, so a Java client outside UTC works. A POSIX rule with daylight saving time and an offset of more than 18 hours are `0A000`. The engine API has no session and reads and writes a `timestamptz` in UTC. Compared with PostgreSQL 18, pgjdbc, psycopg, and SQLAlchemy (`PostgreSQLTimeZoneTest`); see the [differences page](postgresql-differences.md#not-built-yet). Fork issues [#237](https://github.com/humemai/arcadedb/issues/237) and [#270](https://github.com/humemai/arcadedb/issues/270). |
| A value the record cannot hold as PostgreSQL does: a JSON array or scalar into a `MAP`, a key `@type` at the top of one, a null element in a typed list or a primitive array, an array of two or more dimensions, an `EMBEDDED` property without a declared document type, a collection of links | refused, `0A000` | Fork issue #138. `NULL` and `DEFAULT` work for these columns too. |
| `INSERT ... ON CONFLICT DO NOTHING`, with or without `(column, ...)` | supported | A row that breaks a unique index is skipped and not counted. With a target only the index on exactly those columns is an arbiter; a break of another index is `23505`. A target that no unique index matches is `42P10`. |
| `INSERT ... ON CONFLICT (column, ...) DO UPDATE SET ... [WHERE ...]` | supported | The row that is there is read by the table name or the alias, the proposed row as `EXCLUDED`; a bare column that both have is `42702`. A row that would change what the same statement wrote is `21000`. `DO UPDATE` without a target is `42601`. |
| `ON CONFLICT ON CONSTRAINT`, an expression or a predicate in the target, `ON CONFLICT` on an edge table | refused, `0A000` | Name the columns of the unique index instead. |
| `function(...) OVER ([PARTITION BY ...] [ORDER BY ...])` for `row_number`, `rank`, `dense_rank`, `lag`, `lead`, `first_value`, `last_value` and `count`, `sum`, `avg`, `min`, `max` | supported | The default frame of PostgreSQL: to the last peer of the row, the whole partition without `ORDER BY`. In the select list and in `ORDER BY` only: in `WHERE` or `GROUP BY` it is `42P20`. A name that is no window function is `42883`. |
| An explicit frame (`ROWS`, `RANGE`, `GROUPS`), a named window, `DISTINCT`, `ntile`, `percent_rank`, `cume_dist`, `nth_value`, `string_agg`, `array_agg` and `jsonb_agg` over a window, `ORDER BY` inside a window aggregate, a window function in a query with `GROUP BY`, `HAVING` or an aggregate | refused, `0A000` | |
| `a CROSS JOIN b`, chains of them, and mixed with `INNER` and `LEFT` joins | supported | Every pair of rows: a nested loop that holds the right input in memory under the memory cap (`53200` over it), or a hash join when a `WHERE` term over both sides is an equality, as with `FROM a, b`. `CROSS JOIN ... ON` and `... USING` are `42601`. `NATURAL JOIN` stays refused, `0A000`. |
| The memory cap of an operator that keeps rows (hash join build, `GROUP BY`, derived table, `WITH`, set operation, subquery key set) | supported | One operator may keep a sixteenth of the maximum heap of the JVM in estimated row bytes, at least 64 MiB and at most 1 GiB (a JVM with 2 GiB: 128 MiB; with 4 GiB: 256 MiB). Over it the statement stops with `53200` and a hint, never an answer from part of the rows. The JVM property `arcadedb.postgresql.joinMemoryMb` (MiB) sets it. A `GROUP BY` counts each group it keeps (its key values and the state of its aggregates), not the input rows; what one group collects (the values of `count(DISTINCT x)`, the text of `string_agg`) is not counted. |
| The record id `rid` of a type, edge types included (a table that `CREATE TABLE` made lists it once an end of an edge table that holds record ids, or a `LINK` property, refers to the table), in `information_schema.columns` and `pg_attribute` | supported | Reported as `GENERATED ALWAYS AS IDENTITY`: `is_identity` `YES`, `identity_generation` `ALWAYS`, `column_default` NULL, `is_nullable` `NO`, `attidentity` `a` (the start, increment, maximum and minimum of an identity are NULL, the column is `text`). A client that reads the columns leaves them out of an `INSERT`, as it does against PostgreSQL. Unlike PostgreSQL, `atthasdef` is true and `pg_attrdef` holds the default `arcadedb_record_id()` (a label, not a function), which makes the SQLAlchemy ORM read a new key back with `RETURNING` (`PostgreSQLCatalogClientsTest`, fork issue #137). `psql` prints `generated always as identity`. |
| `id` in a table that declares no column `id`: `SELECT id`, `WHERE id = ...`, `max(id)`, `INSERT INTO t (id) ...`, `RETURNING id` | refused, `42703` | As in PostgreSQL. The record id is read as `rid` only, and the hint says `no column id: read rid, or declare id bigserial PRIMARY KEY`. Fork issue [#240](https://github.com/humemai/arcadedb/issues/240). |
| A value for a record id column: `INSERT INTO t (rid, ...) VALUES ('#9:1', ...)`, `UPDATE t SET rid = ...` | refused, `428C9` | As PostgreSQL refuses a value for `GENERATED ALWAYS`: the engine gives the record id and a statement cannot choose it (a record cannot be created at a chosen position). `DEFAULT` is accepted and means the engine's value. `OVERRIDING SYSTEM VALUE` and `OVERRIDING USER VALUE` are refused, `0A000`. |
| Foreign keys in `information_schema`, `pg_constraint`, and `pg_get_constraintdef` (so also `\d` in `psql`, pgjdbc, and SQLAlchemy reflection) | supported | Listed for the foreign keys between ordinary tables (with their `ON DELETE` and `ON UPDATE` rules, enforced), for the declared ends of an edge type, and for `LINK` properties. A key of an edge end on record ids has delete rule `CASCADE` (`confdeltype` `c`, `ON DELETE CASCADE`), because deleting a vertex deletes its edges. An end that refers to a key has its declared rules (`confdeltype` and `confupdtype`). A key of a `LINK` column is not enforced (`enforced` `NO`, `conenforced` false, `NOT ENFORCED`): a write through this language refuses a link to a missing record (`23503`), but the referenced record can be deleted. |
| `gen_random_uuid()` | supported | A random (version 4) `uuid`, one per row, also as the `DEFAULT` of a `uuid`, `text`, or `varchar` column (`gen_random_uuid()::text` too, for the last two). In the schema the default is `uuid()` of ArcadeDB `sql`, so a record that another language creates takes one too. |
| The type `uuid`: a column, a cast, parameters in text and binary, comparisons, `ORDER BY`, `GROUP BY`, keys, indexes, and foreign keys | supported | The record holds the 36 characters in lower case, and the schema refuses any other text from every language. No `uuid[]`, `uuidv4()`, or `uuidv7()`. Compared with PostgreSQL 18, pgjdbc, psycopg, and SQLAlchemy (`PostgreSQLUuidTest`). Fork issue [#225](https://github.com/humemai/arcadedb/issues/225). |
| `a RIGHT [OUTER] JOIN b` and `a FULL [OUTER] JOIN b`, with `ON` or `USING` | supported | `RIGHT` keeps the rows of `b` that no row of `a` matches, `FULL` keeps both sides, with `NULL` on the missing side. A `WHERE` term stays above the join, as in PostgreSQL. With `USING` the merged column is `b`'s for `RIGHT` and `coalesce(a, b)` for `FULL`. A hash join (an equality in the condition) or, for `RIGHT` and for `FULL ... ON true`, a nested loop, each holding one input in memory under the memory cap (`53200` over it); never an index lookup or a walk. A `FULL JOIN` whose condition has no equality is `0A000`, as in PostgreSQL, and so is `FULL JOIN ... USING` on columns whose types cannot be hashed. `NATURAL` joins stay refused, `0A000`. |
| `x = ANY (array)`, `x <> ALL (array)`, and `=`, `<>`, `<`, `>`, `<=`, `>=` with `ANY`, `SOME`, or `ALL` over an array: `ARRAY[...]`, a literal (`'{1,2}'`), a column, a cast, or a parameter that a driver binds as an array (`id = ANY(?)`) | supported | The three-valued logic of PostgreSQL: `NULL` for a `NULL` array, false (`ANY`) or true (`ALL`) for an empty one. A value that is no array is `42809`, and types that do not compare are `42883`. An array of one dimension of booleans, numbers, text, dates, or timestamps. The table is read as for `IN`, without an index. Compared with PostgreSQL 18, pgjdbc, and psycopg (`PostgreSQLArrayAnyTest`). Fork issue [#233](https://github.com/humemai/arcadedb/issues/233). |
| `x = ANY (SELECT ...)`, `x <> ALL (SELECT ...)` | supported | As `IN` and `NOT IN`. Another comparison with `ANY` or `ALL` of a subquery is refused, `0A000`: write it with `EXISTS`. So are other operators with `ANY` or `ALL`, such as `LIKE` and `~`. |
| The array operators `@>`, `<@`, `&&`, `=`, and `<>`, and `IS [NOT] DISTINCT FROM` of arrays | supported | As PostgreSQL: both arrays of one element type (`42883` otherwise), a literal or a parameter of no declared type takes the type of the other side, `NULL` elements are equal to each other for `=` and to nothing for `@>`, `<@`, and `&&`. The table is read without an index. Ordering arrays (`<`, `>`, `ORDER BY`) is not part of it: `<`, `<=`, `>`, `>=` are refused, `0A000`. One difference: a bound `varchar[]` compares with a `text[]`, where PostgreSQL answers `42883`. Compared with PostgreSQL 18 (`PostgreSQLArrayOperatorTest`). Fork issue [#233](https://github.com/humemai/arcadedb/issues/233). |
| `a IS DISTINCT FROM b`, `a IS NOT DISTINCT FROM b` | supported | Two NULLs are the same, a NULL and a value are different, the answer is never NULL. Typed as `=` is: a mismatch of types is `42883`. |
| `power` of `double precision` with `NaN` or infinity | supported | The answers of PostgreSQL 18: `power(1, 'NaN')` and `power(-1, 'inf')` are `1`. Fork issue [#188](https://github.com/humemai/arcadedb/issues/188). |
| `OVER (... ROWS UNBOUNDED PRECEDING)` and `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` | supported | The frame ends at the current row, not at its last peer (aggregates and `last_value`). Any other frame, `n PRECEDING`, `FOLLOWING`, `RANGE`, `GROUPS`, `EXCLUDE`, stays `0A000`. |
| `VALUES (...), (...)` as a query: `FROM (VALUES (1, 'a'), (2, 'b')) AS t(a, b)`, `IN (VALUES ...)`, `WITH v AS (VALUES ...)`, `VALUES ... ORDER BY ... LIMIT`, a statement of its own | supported | A constant table. Its columns are typed as `UNION` types them (an unknown literal is `text` unless the other rows say otherwise, `1` and `2.5` make `numeric`, `1` and `'x'` is `22P02`) and named `column1`, `column2` when there is no alias list. Rows of different widths and `DEFAULT` are `42601`. More than 500 rows, `LATERAL (VALUES ...)` and `TABLE t` are refused, `0A000`. `INSERT ... VALUES` is the separate statement and still takes `DEFAULT`. |
| A subquery in a write: `IN`, `NOT IN`, a scalar subquery and `EXISTS` in the `WHERE`, `SET` and `VALUES` of `INSERT`, `UPDATE` and `DELETE` | supported | The subquery is planned as in a `SELECT` and sees the table as it was before the statement (it runs on the first row, the writes come after every match is found). `VALUES ((SELECT rid FROM ...), ...)` gives the ends of an edge that holds record ids. |
| A correlated `EXISTS` or `NOT EXISTS` whose `WHERE` has terms that are not key equalities: a comparison, an `OR`, a term of the outer query alone, an expression over both sides inside a comparison or an arithmetic operator | supported | The equalities pick the candidate rows by hash, the other terms are tested on them with the three-valued logic of PostgreSQL; with no equality every row is a candidate. A scalar or `IN` subquery in a term counts with every column that it reads of either query (fork issue [#164](https://github.com/humemai/arcadedb/issues/164)). A term that mixes both sides inside a function, a `CASE`, or one such subquery, and a correlated `EXISTS` with `GROUP BY`, `HAVING`, `LIMIT` or an aggregate, stay `0A000`. |
| Number text in another notation, as a value of `int2`, `int4`, `int8`, or `numeric`: `'0x1F'`, `'0o17'`, `'0b101'`, and `_` between digits (`'1_000'`) | supported | Read as PostgreSQL 18 reads it: `22003` for a number that does not fit an integer type, `22P02` for a text that is no number.
